# World design preview

In an explicitly enabled Creative project, select **Plan or revise my project**
above the chat composer. Describe the places, landscape and style you want. The
application retains explicit requirements independently of the local provider. Put
each named place on its own line, for example:

```text
Plan a 192 by 192 river town with a natural palette.
River: water 12 by 192, 4 blocks high, elevation -4.
Inn: building 20 by 16, 10 blocks high, west. Two-storey. Rooms: common room, kitchen, four upstairs rooms. Connects to River.
```

The requirements checklist shows dimensions, shapes, rotation, rooms, connections,
object inventories and the source wording. Small model proposals fill remaining
layout choices; they cannot rewrite explicit facts. Each accepted batch becomes a
saved version. Drafting never changes world blocks. Unknown notes, unresolved
connections and conflicting footprints keep the design pending for clarification.
The parser supports named descriptions and targeted changes, not arbitrary prose.
“Requirements matched” means the saved planning records match the checklist; it
is not a claim that rooms, paths or terrain have been generated or verified in-game.

## Review and edit

The preview shows footprints, approximate elevation/massing, palette, planned
connections, a protected outer buffer and bounding-volume estimates. These are
planning aids, not surveyed terrain, verified walking routes or completion-time
promises. Blue outlines identify changed components; purple dashes show previous
footprints. Existing versions remain in the project database.

Ask for a targeted change in chat, or expand **Edit a place** to choose its shape,
dimensions, area, elevation and rotation. Editing a place preserves the other
components. Contradictory bounds or overlapping building footprints are refused.
An explicitly stated 192×192 or 256×256 extent is enforced independently of model
output. No model-proposed deletion is admitted by the chat schema.

Reference intake accepts up to six local PNG/JPEG images, each at most 4 MB and
16 million pixels, with a caption explaining its intended use and source. Images
and captions persist in the same project database. No remote image fetching occurs.
The current designer uses captions only: image analysis is unavailable, and local
image previews do not establish visual understanding or replica fidelity.

## Build a small component sample

Only an open pavilion or platform with a 3–12 block footprint and 3–8 block height
currently has a compiler. Select it, choose **Prepare selected preview**, review,
then **Build selected preview**. This builds a component sample at the local enabled
preview site, not at its full-project destination. Terrain, arbitrary buildings and
native functional objects are still planning-only. Raised samples receive supports.

Preparation performs inspection only. Execution uses the existing 64×64 region,
100,000-cell maximum, 64-cell units, protection checks and construction journal.
The full-plan extent does not grant larger write authority. A revised design needs
fresh preparation; an obsolete selection or session cannot start the selected build.
Stop and reopening restore no running task. Continue remains an explicit action.

## Implementation boundaries

`minecraft_design.py` owns brief versions, component layout and references in the
existing `BuildProject` SQLite database. `minecraft_chat.py` owns admission and
late-result rejection. `minecraft_requirements.py` owns pure extraction, provenance and checklist validation.
Planning uses batches of at most three components, at most 32 model calls and a
20-minute operation deadline. Each batch permits one visible validation-repair
attempt; transport failures are not retried automatically. The configured
512-token/240-second per-call bounds remain. The UI shows call/time consumption.
Partial requirements and accepted batches survive failure or Stop; use **Continue
planning** explicitly after resolving issues. Reopening never resumes inference.

`minecraft_build.py` remains the only execution transaction owner, including
reviewed terrain region expansion. `minecraft_terrain.py` compiles landscape geometry
without world I/O. `minecraft_architecture.py` compiles reviewed buildings and interiors without world I/O.
Recipe questions use read-only facts from the connected worker's existing crafting
registry; displayed answers describe a verified example rather than an exhaustive
recipe claim generated by the model.

Focused checks:

```bash
.venv/bin/python -m pytest -q tests/test_minecraft_requirements.py tests/test_minecraft_design.py tests/test_minecraft_chat.py tests/test_minecraft_chat_ui.py tests/test_ai_provider.py
node --test minecraft-worker/test/*.test.cjs
```

`scripts/qualify_minecraft_design.py` is an explicitly authorized live harness. It
uses a fresh output directory and disposable world, records actual provider results,
and saves/shuts down owned processes. The `--requirements` mode submits the authored island/town briefs from
`data/minecraft/design-briefs.json` through ordinary chat, checks requested facts
and targeted revisions, and builds a separately chat-requested small pavilion.
Those files are test inputs, not a product-specific generator. The legacy mechanism
continuation tests explicit editor correction only; it cannot establish brief fidelity.
The harness must never target owner worlds.

## Landscape construction

After requirements are resolved, choose **Review terrain**, inspect the elevation
map, reserved sites, bounds and planned work, then **Start / continue terrain**.
Review does not write blocks. The landscape supports coastlines, contained water,
stepped hills, beaches, woodland patches, paths, terraces and bounded caves.
Actual reserved-site positions are shown because the terrain interpretation can
move a crest or raised site to preserve heights and clear access.

Stop leaves journaled partial work; reopening stays idle. Continue explicitly after
inspection. New coast/elevation requirements produce a new reviewed manifest and
retain verified unaffected stages. Water is resealed before affected cuts, so even
a small edit can take time. Architecture, interiors and native objects remain
reserved plans unless separately built and verified. See [construction and recovery](minecraft-build-service.md).

## Buildings and interiors

After terrain completes, choose a place and materials under **Buildings and
interiors**, review its room/object inventory and dependencies, then build. The
generic compiler supports partitioned buildings, two storeys, lofts, shallow
asymmetric or steep roofs, towers with stairs, pavilions, docks and decorative
wrecks. Reusable objects include awnings, stalls, furniture, crates, bollards and
static wheels. The review distinguishes decorative assemblies from native doors,
containers, beds, workstations and lighting. Signpost assemblies are decorative
markers; their destination labels appear in the review, not native sign text.

Material changes target the selected place. The glass material uses glazed walls
and roof with a stone floor; choose it explicitly in architecture review. Changed footprints or elevations need
a separate terrain review. **Review updated paths around buildings** creates a
new review version without moving places; inspect it before starting terrain.
Terrain execution preserves architecture-owned blocks and interior air, and
refuses foundation/water changes under retained architecture. Stop and reopening
never resume work automatically. Partial outcomes remain visible.

A saved room count alone does not prove access or usable interiors. Inspect the
completed world before relying on it; block-state recovery does not restore
container contents.
